# Claude Code Instructions

## Security

- Never read secrets files (e.g., `.env.secrets`, credentials files, or anything in a `secrets/` directory)

## Scripting patterns for agents

- **Capture IDs at the source.** `POST /jobs/create` returns the new bounty in `cr.job.jobId` — read it from the response. Never re-search `/jobs` for something you just created; that endpoint has async indexing lag (jobs are synced from on-chain events, so they can be missing for seconds after creation).
- **Split long flows into phase scripts.** For flows with a known wait (an evaluation round — draw, commits, reveals — is ~5–10 min, longer for large juries), write separate short-lived scripts: (1) create+submit → exits printing IDs, (2) wait out-of-band, (3) check status + finalize → exits. Do not structure as one backgrounded script with a poll loop — background sessions have finite lifetime and will race the harness's session tracking, producing synthetic errors even when the underlying work succeeded.
- **Never create an API job without deploying its on-chain bounty.** Each `POST /jobs/create` auto-increments the API's `jobId` counter, which must stay aligned with on-chain `bountyCount`. Calling `/jobs/create` without immediately following it with `createBounty` on-chain + `PATCH /jobs/:jobId/bountyId` drifts the counters. To debug request shapes, use the side-effect-free validators — `POST /api/jobs/rubric/validate` for rubric shape, `POST /api/jobs/validate` for an evaluation-package CID, `POST /api/jobs/:id/submit/dry-run` for submission files — never `/jobs/create`. Since v1 of this guard, the server rejects calldata endpoints (`/submit`, `/submit/bundle`, `/submit/bundle/complete`, `/submit/prepare`, `/submissions/:subId/start`, `/finalize`, `/approve-as-creator`, `/close-failed` (`/timeout`), `/draw`, `/rerun`, `/close`) for un-linked jobs with `400 BOUNTY_NOT_ONCHAIN` — a "linked" job has `onChain === true` (set by PATCH) or `syncedFromBlockchain === true` (set by the sync service via BountyCreated event match).
- **Pass nested JSON fields as native objects/arrays, not strings.** `rubricJson` and `juryNodes` on `POST /jobs/create` are nested JSON — the request body is already JSON, so do NOT pre-stringify them. `rubricJson: { criteria: [...] }`, not `rubricJson: "{\"criteria\":[...]}"`. The server now rejects stringified values with a clear 400, but the failure mode used to be a misleading "Missing or invalid criteria array".
- **Contract rules that trip agents (v2 aggregator, November 2026 revision).** `createBounty` takes ONE struct (`CreateParams`): an `oracle` sub-struct of creator-chosen `maxOracleFee/alpha/estimatedBaseCost/maxFeeBasedScaling/minOracleFee/withBeacons`, plus `jury` (the bounty's own jury STRUCT `{K, M, N, P, timeout}`: K drawn, M promoted, N counted, P clustered, round timeout in seconds; checked at create: K >= M >= N >= P >= 1, N <= 40, P >= 2 unless N = 1, quota <= N; `getBounty` returns it flat as `juryK`, `juryM`, `juryN`, `juryP`, `juryTimeout`; NOT an aggregator index — the escrow has ONE immutable `aggregator()` serving every jury size, each request carries the jury, and a round's jury reads back with the aggregator's `getJury(aggId)`), `quota` (Q: arbiter scores at or above the threshold needed to pass), `forfeitLine` (R <= Q) and `bond` (wei, posted by whoever starts). Size-class defaults live in `shared/classPresets.js` (`GET /api/classes/presets`); the creator may override every value. `prepareSubmission` is 3 args `(bountyId, evaluationCid, hunterCid)`; hunters supply no oracle parameters (the bounty's settings are used, clamped to the aggregator's live fee ceiling at start — `effectiveOracleParams(bountyId)`). `hunterCid` must be a bare CID (46–100 alphanumeric chars; `bad hunterCid` otherwise). Windowed bounties cap prepares at 128; every bounty caps CONCURRENT evaluations at 64 (`evaluation slots full - retry later`; a slot frees when an in-flight round resolves). Start attaches `msg.value == startValue(bountyId)` (= `requiredPrepay` + bond) read LIVE, before the deadline. A started round must then be DRAWN: `drawJury(bountyId, submissionId)` from 2 blocks after start (anyone; twice for beacon juries), then arbiters commit, `closeCommits(aggId)` / `promote(aggId)` go to the escrow's aggregator (`aggregator()`; anyone, the caller earns the reward), arbiters reveal, and `finalizeSubmission` applies the Q-of-N rule: pass (>= Q) pays and returns the bond; soft fail (R..Q-1) or a round with no result → `AwaitingRerun` (status 6): the hunter or bond funder may `rerunSubmission` (payable `requiredPrepay`) within 2 hours (`rerunDeadline`), up to 6 rounds, else anyone may `expireRerun` (bond returned); hard fail (< R) → Failed, bond to the creator. A dead round (failed or cancelled; past its deadline; or undrawn and cancellable: about 8,191 blocks, ~27 minutes, after the start if its seed was never stored, a day after it if it was sealed but never drawn, the cancelled round's whole prepay going to the aggregator's treasury) is closed with `closeFailedRound` (replaces `failTimedOutSubmission`; there is no fixed 300 s timeout). The server's keeper (`KEEPER_PRIVATE_KEY`) usually sends draw/close/promote/closeFailedRound/expireRerun itself; calldata endpoints exist for each (`/draw`, `/round-step`, `/close-failed` (alias `/timeout`), `/rerun`, `/expire-rerun`). Any finalize may revert `earlier submission pending - retry after it resolves` — payout priority is by submission index among in-flight AND AwaitingRerun submissions by other hunters (protects originals against copied CIDs); it is not a failure. `POST /finalize` then returns `nextAction: "AWAIT_EARLIER"` and `blockedBy[]`, each with the `transaction` that resolves it when it is FINALIZE / CLOSE_FAILED / EXPIRE_RERUN (anyone may send it; it cannot change who wins). Payouts to contract wallets may land on the pull ledger (`PaymentDeferred`) — claim with `withdraw()`. If a resolving tx emits `RefundDeferred`, recover the prepay via `recoverLeftoverEth(bountyId, submissionId)` (API: `POST /submissions/:subId/recover-refund`). When unsure, ask the contract: `nextAction(bountyId, submissionId)` (also `diagnosis.nextAction` on `/diagnose`) returns START / AWAIT_SLOT / AWAIT_CREATOR / DRAW / CLOSE_COMMITS / PROMOTE / AWAIT_ORACLE / AWAIT_EARLIER / FINALIZE / CLOSE_FAILED / RERUN / AWAIT_EXPIRY / EXPIRE_RERUN / RECOVER_REFUND / DONE / DEAD — always the call that will succeed now. `getOracleResult` gives the round's phase, outcome (not_ready / no_result / pass / soft_fail / hard_fail), passCount, rounds and deadline without the aggregator ABI; `getSubmissions` / `getBounties` batch-read; `prepareCutoff` gives the last second prepare works. `/submit/prepare` returns the SubmissionPrepared descriptor — use it.
- **Read revert reasons, not the ethers formatted error.** When a submission transaction reverts, ethers' stringified error often shows `data: ""` even when the real revert reason is on the receipt. During submission, the most common real cause is the wallet's ETH balance being below `ethMaxBudget` (the oracle prepay) plus gas — `startPreparedSubmission` is `payable` and you must attach `msg.value == startValue(bountyId)` (prepay + bond) read LIVE from the escrow (the prepare-time `ethMaxBudget` is only an estimate; it reverts with "wrong eth amount" if the value is off, or "insufficient funds" if the wallet can't cover it). The `/start` endpoint's `transaction.value` is the live value. Check the wallet's ETH balance before debugging calldata.
