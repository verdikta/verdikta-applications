# Claude Code Instructions

## Security

- Never read secrets files (e.g., `.env.secrets`, credentials files, or anything in a `secrets/` directory)

## Scripting patterns for agents

- **Capture IDs at the source.** `POST /jobs/create` returns the new bounty in `cr.job.jobId` — read it from the response. Never re-search `/jobs` for something you just created; that endpoint has async indexing lag (jobs are synced from on-chain events, so they can be missing for seconds after creation).
- **Split long flows into phase scripts.** For flows with a known wait (oracle evaluation is ~5–10 min), write separate short-lived scripts: (1) create+submit → exits printing IDs, (2) wait out-of-band, (3) check status + finalize → exits. Do not structure as one backgrounded script with a poll loop — background sessions have finite lifetime and will race the harness's session tracking, producing synthetic errors even when the underlying work succeeded.
- **Never create an API job without deploying its on-chain bounty.** Each `POST /jobs/create` auto-increments the API's `jobId` counter, which must stay aligned with on-chain `bountyCount`. Calling `/jobs/create` without immediately following it with `createBounty` on-chain + `PATCH /jobs/:jobId/bountyId` drifts the counters. To debug request shapes, use the side-effect-free validators — `POST /api/jobs/rubric/validate` for rubric shape, `POST /api/jobs/validate` for an evaluation-package CID, `POST /api/jobs/:id/submit/dry-run` for submission files — never `/jobs/create`. Since v1 of this guard, the server rejects calldata endpoints (`/submit`, `/submit/bundle`, `/submit/bundle/complete`, `/submit/prepare`, `/submissions/:subId/start`, `/finalize`, `/approve-as-creator`, `/timeout`, `/close`) for un-linked jobs with `400 BOUNTY_NOT_ONCHAIN` — a "linked" job has `onChain === true` (set by PATCH) or `syncedFromBlockchain === true` (set by the sync service via BountyCreated event match).
- **Pass nested JSON fields as native objects/arrays, not strings.** `rubricJson` and `juryNodes` on `POST /jobs/create` are nested JSON — the request body is already JSON, so do NOT pre-stringify them. `rubricJson: { criteria: [...] }`, not `rubricJson: "{\"criteria\":[...]}"`. The server now rejects stringified values with a clear 400, but the failure mode used to be a misleading "Missing or invalid criteria array".
- **Contract rules that trip agents (September 2026 revision).** `createBounty` takes ONE struct (`CreateParams`, with an `oracle` sub-struct of creator-chosen `maxOracleFee/alpha/estimatedBaseCost/maxFeeBasedScaling`) — no overloads. `prepareSubmission` is 3 args `(bountyId, evaluationCid, hunterCid)`; hunters supply no oracle parameters at all (the bounty's settings are used, clamped to the aggregator's live fee ceiling at start — `effectiveOracleParams(bountyId)`; `ethMaxBudget` is the same for every submission to a bounty at any moment). `hunterCid` must be a bare CID (46–100 alphanumeric chars; `bad hunterCid` otherwise). Non-windowed bounties have NO cap on prepared submissions; WINDOWED bounties cap prepares at 128 (`submission limit reached`). Every bounty caps CONCURRENT evaluations at 256 — `startPreparedSubmission` reverts `evaluation slots full - retry later` while `activeEvaluations(bountyId)` is at the cap; a slot frees when any in-flight round resolves (finalize or force-fail, both callable by anyone), so retry, it is not a failure. `pendingSubmissionIds(bountyId)` lists the in-flight ids; `getSubmissionsPage(bountyId, start, count)` pages submissions (non-windowed bounties can hold thousands). `failTimedOutSubmission` has no timer — it works only once the aggregator round timed out with no result (`evaluation not settled` / `result available - use finalizeSubmission`). Start must happen before the deadline (`deadline passed`). Any finalize may revert `earlier submission pending - retry after it resolves` — payout priority is by submission index among in-flight submissions (a later passing submission waits for earlier ones by other hunters; protects originals against copied CIDs) — it is not a failure. The earlier submission is often already evaluated and merely unfinalized: `POST /finalize` then returns `nextAction: "AWAIT_EARLIER"` and `blockedBy[]` (each earlier submission with its `nextAction` and, for FINALIZE / FORCE_FAIL, the `transaction` that resolves it — anyone may send it; it cannot change who wins). Send those, then your own finalize; only AWAIT_ORACLE blockers must be waited out. Start promptly after preparing: only submissions in evaluation hold priority. Payouts to contract wallets may land on the pull ledger (`PaymentDeferred` event) — claim with `withdraw()`. If a resolving tx emits `RefundDeferred`, the oracle prepay is recovered later via `recoverLeftoverEth(bountyId, submissionId)` (anyone may call; pays the funder; API: `POST /submissions/:subId/recover-refund`). When unsure what to do with a submission, ask the contract: `nextAction(bountyId, submissionId)` (also `diagnosis.nextAction` on `/diagnose`) returns START / AWAIT_SLOT / AWAIT_CREATOR / AWAIT_ORACLE / AWAIT_EARLIER / FINALIZE / FORCE_FAIL / RECOVER_REFUND / DONE / DEAD — always the call that will succeed now (the two AWAIT_* additions mean retry later: concurrency cap reached, or a passing result waiting for an earlier in-flight submission); `getOracleResult` polls the oracle without the aggregator ABI; `getSubmissions` / `getBounties` batch-read; `prepareCutoff` gives the last second prepare works. `SubmissionPrepared` now emits `ethMaxBudget` BEFORE the `evaluationCid` string (topic0 `0x147341…d6ca`); `/submit/prepare` returns the descriptor — use it.
- **Read revert reasons, not the ethers formatted error.** When a submission transaction reverts, ethers' stringified error often shows `data: ""` even when the real revert reason is on the receipt. During submission, the most common real cause is the wallet's ETH balance being below `ethMaxBudget` (the oracle prepay) plus gas — `startPreparedSubmission` is `payable` and you must attach `msg.value == requiredPrepay(bountyId)` read LIVE from the escrow (the prepare-time `ethMaxBudget` is only an estimate; it reverts with "wrong eth amount" if the value is off, or "insufficient funds" if the wallet can't cover it). The `/start` endpoint's `transaction.value` is the live value. Check the wallet's ETH balance before debugging calldata.
